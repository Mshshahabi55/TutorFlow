## Remaining blockers before further scaffolding

With A1–A8, A14–A16, A18–A30, #1, #6, #14, #16, #18, #19, #30, #31, #32, and #33 resolved, the repository is unblocked for the `Identity`, `Tutors`, `Availability`, and now (at the specification level — not yet implemented, and as of 2026-10-04 passed a strict architecture review with all findings corrected, plus a full V1 business-policy decision pass the same day) `Bookings` modules (see `ADR-0002`, `ADR-0011`, `ADR-0012`, and `ADR-0013`–`ADR-0017` + `docs/domain/BOOKINGS_SPEC.md`). Remaining genuinely open items that block *other* modules specifically:

- **Subscriptions**: cycle length, pricing, credits-per-cycle, rollover, cancellation/proration rules (#20–#24) — blocks all `Subscriptions` scaffolding.
- **Payments production payout/tax** (see the dedicated section below): earnings accrual timing, payout frequency/minimum/fees, VAT/tax/invoicing (#12, #13, #29) — blocks payout/tax features specifically, not `Payments`' first feature (PaymentIntent creation via Stripe Connect Express) generally. `Bookings`' `PendingPayment`→`Confirmed`/`Cancelled`→`Refunded` transitions cannot be exercised end-to-end until `Payments` exists either (`ADR-0015`), though the idempotency/ordering contract `Payments` must honor is now fully specified (A30), and the business policy driving *when* a refund is requested is now locked (`ADR-0015` §6).
- **`Payments` itself, now fully specified at the design level** (`docs/domain/PAYMENTS_SPEC.md`, `ADR-0018`) **but blocked on one genuine architectural conflict**: A31 (`ADR-0019`) — the synchronous call `Bookings` must make for checkout/refund-request doesn't fit either sanctioned cross-module mechanism. Also newly open and blocking the first implementation slice specifically (not payout/tax): commission/take-rate (#34), Stripe Connect charge-type confirmation (A32). Newly identified implementation prerequisites, not conflicts: a `Bookings`-side handler for webhook-triggered cancellation (A33), introducing Wolverine for the first time (A34), and an `Admin` role/policy that doesn't exist in `Identity` yet (A35).
- **Bookings/Lessons remaining business rule**: who/what marks lesson completion (#17) — blocks that one finer transition rule, not the base state machine shape (already accepted and, as of A28, fully reconciled into one table; no-show/cancellation/refund policy is now locked, see #6/#16/#18 above). `Bookings`' `BookingConfirmed`/`BookingCancelled` events cannot be consumed until `Lessons` exists (`ADR-0016`).
- **Admin sub-roles** (#2) — blocks fine-grained Admin authorization policy design, not Identity's core multi-role model.
- **A13 (Money in Shared)** — explicitly still deferred until `Payments`' design is reviewed; `Tutors` and (per `BOOKINGS_SPEC.md` §1.2) `Bookings` each keep their own local `Money` type in the meantime. The currency-value decision (#4, EUR-only for v1) does not require resolving A13 — it constrains which currency is accepted, not where the `Money` type lives.
- **`Availability`-side prerequisites before `Bookings` can be implemented against it** (`ADR-0014`, `BOOKINGS_SPEC.md` §5 — now four, fully specified, none yet implemented): (1) generalized duration-aware slot validation; (2) a new public, non-self-service slot-browsing endpoint; (3) that endpoint consuming the new reciprocal `IActiveBookingIntervalsQuery` (A29) so it never shows a `Bookings`-held slot as open; (4) `ADR-0011`'s `Tutors`→`Availability` publish/consume pipeline actually wired, with a fail-closed ("not bookable") default documented for any tutor it hasn't yet run for. Also still open from `ADR-0012`: how the onboarding wizard's Booking Settings step reaches `Availability`.
- Everything else listed under Product Owner / Architect decisions below remains open as before.

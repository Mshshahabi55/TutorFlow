# Domain Model

Maps the 14 fixed bounded contexts to product responsibility, tentative key entities, and known gaps. Module boundaries themselves are **already decided** (`docs/decisions/ADR-0001-module-boundaries.md`, Accepted) — this document does not propose changing them. It proposes what goes *inside* each one, which is not yet decided.

## Known structural gaps

### 1. Classroom ownership — Resolved

The brief describes "Classroom" (video, chat, file sharing, notes, screen sharing, learning materials, homework, lesson info) as a product feature area, but it is not one of the 14 bounded contexts. **Resolved** per `ADR-0006`: `Lessons` owns the live classroom session (chat/notes/file-sharing-during-the-session, video/session provider abstraction); `Learning` owns persistent materials/homework/progress (content that outlives a single session). No separate `Classroom` bounded context is created.

### 2. Admin is not a bounded context — Resolved

See `ADMIN_JOURNEY.md` and `ADR-0008` (Accepted). Composed-admin (each module exposes its own admin contract) is the adopted model; no 15th "Admin" module is created.

### 3. Promotions, Support-as-ticketing, Reports, Feature Flags, Audit Logs

None of these map onto an existing module. They are not silently assigned anywhere in this document — see `OPEN_QUESTIONS.md`.

## Shared kernel (`TutorFlow.Shared`) — current and anticipated contents

Per `CLAUDE.md`, `Shared` holds only contracts and cross-cutting primitives, never business logic. Current: `IIntegrationEvent`. Anticipated additions, consistent with that rule (these are primitives, not business rules):

- A **Money** type (integer minor units + ISO 4217 currency code) — needed by Payments, Subscriptions, Tutors (pricing)
- A **UTC instant + source timezone** pairing convention — needed by Bookings, Availability, Lessons
- **Added (2026-10-04, `ADR-0020`)**: a **`LanguageCode`** primitive (validated ISO 639-1 string) — needed by `Tutors` (`TutorSpokenLanguage`), `Subjects` (the admin-curated enabled-languages list), and `Search` (the `TutorSearchDocument` spoken-languages projection). A primitive shape only, no behavior — same rationale as `Money`/ISO 4217.
- Integration event contracts for cross-module communication (one record type per event, added as each producing module defines them — not pre-built speculatively)
- **Specified, not yet added** (`ADR-0014`): read-only, synchronous cross-module *query* contracts — e.g. `ITutorAvailabilityQuery`, `ITutorPricingQuery`, the reciprocal `IActiveBookingIntervalsQuery` (owned by `Bookings`, consumed by `Availability`'s browse-slots endpoint), and (added 2026-10-04, `ADR-0019`) `IBookingCheckoutEligibilityQuery` (owned by `Bookings`, consumed by `Payments` to validate a checkout call without trusting caller-supplied amount/currency) — defined as interfaces here, implemented by the owning module, consumed via DI by the calling module. This is a narrow, explicitly-scoped exception to "events only," reserved for idempotent reads a write (or an accurate read) cannot proceed without — never for commands or anything with a side effect. Four instances now exist, all read-only; `ADR-0014`'s scope has not been widened by any of them.

**`[OPEN — Architect]`**: confirm Money and the timezone-pairing convention belong in `Shared` (recommended) rather than being redefined per-module, before the first module that needs money or scheduling times is scaffolded — getting two different modules to define incompatible Money types would be exactly the kind of rework this spec step is meant to prevent. **Still open by explicit decision**: `Tutors` already has its own module-local `Money` value object (amount in minor units + currency) for pricing; this is left as-is for now. A13 is deliberately left open until `Payments`' design is reviewed, rather than guessing the right shared shape from `Tutors`' usage alone.

## Module communication

Unchanged from `CLAUDE.md`: integration events via `TutorFlow.Shared`, transactional outbox once a message bus is introduced (Wolverine recommended, not yet added — see `CLAUDE.md` Tech Stack), no direct project references between business modules, no shared database tables. `Subjects` and `Search` are the clearest near-term example: `Search` needs `Subjects`' taxonomy and `Tutors`' profile data as a denormalized read model, built from consumed events, not a live query across modules.

A second concrete example is now settled at the contract-direction level (though not yet implemented): `Tutors` publishes an event on reaching `Published`, and `Availability` consumes it into its own local read model of tutor bookability, rather than querying `Tutors`' schema directly (`ADR-0011`). As with `Subjects`/`Search`, no messaging infrastructure or concrete event type is added until the consuming module actually needs it.
